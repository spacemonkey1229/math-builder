Overview

The progress bar fills all the way and the word CONVERGED turns green on Priya Kessler's second monitor.

She doesn't move. Behind her, the scan rig's turntable ticks as it cools — six hours of range-image passes, forty-one gigabytes of raw point cloud, all of it now folded down into one aligned mesh sitting in the export queue. On her first monitor, the client's reference model rotates slowly, waiting for the file that's supposed to sit exactly on top of it.

Priya zooms into the mesh's left flank, where pass four met pass five. Something about the seam bothers her. She pulls up the three calibration markers taped to the physical prop before the scan — three known points, logged by hand, that should land in the same place on both the reference model and her scan if the alignment actually worked. Two of them look right. The third one doesn't look wrong, exactly. It looks like it's on the wrong side of the object.

Her phone buzzes, face-down, next to the keyboard. She already knows who it is. The client needs the file by end of day, and if it comes back from their pipeline mis-registered, the studio eats the cost of the whole re-shoot — camera rig, turntable time, her Saturday.

The software says converged. Her eyes say something got mirrored.

Priya picks up the phone without answering it, and opens the marker log.

Background

Priya Kessler is a 3-D scanning and photogrammetry technician at a small VFX digitization studio. Her job is to turn a physical object into a clean, aligned 3-D mesh that matches a client-supplied reference model closely enough for the client's own pipeline to accept it without manual correction. She is accountable for the file she ships — if it fails the client's own registration check after delivery, the studio pays for the re-shoot, not the client.

The scan rig captures the object in multiple passes from different camera positions and stitches them into one point cloud automatically. Its alignment software reports a single word when it's done: converged or failed. It does not report how it converged, and it cannot, on its own, tell the difference between two mesh sections that are related by an ordinary rotation and two that are related by a reflection — a mirror flip. This is a known, documented failure mode in multi-pass photogrammetry: if a camera pass is oriented backward relative to the others, the matching algorithm can pair up mirrored surface features and report a low, "converged" error anyway, because the shape still looks similar even though it is no longer the same object traced through space (see Appendix A).

To catch this, the studio always logs the physical position of three known marker points stuck to the object before scanning starts, and records where the client's reference model says each marker should land ("expected") versus where the finished scan says each marker actually is ("actual") (see Appendix B). If the actual markers are a rotation and translation of the expected markers, the scan is trustworthy. If one marker's actual position looks like a reflection of its expected position instead, part of the scan is mirrored — and the rig's own reported error number cannot be trusted to say so.

Every registration decision at the studio is judged by the same yardstick: how much point-to-point mismatch, in millimeters, is left in the file relative to how many technician minutes it cost to get there (see Appendix D). Any figure in this case that is not a real, sourced number is disclosed plainly as a stated Modeling Assumption (see Appendix E), and every source used to ground this case is listed in full in Appendix G. The vocabulary and "how to…" skills this case sends you to research are listed in Appendix F.

Automatic point-cloud and photo alignment solvers are documented to settle into a self-consistent but geometrically wrong registration when a scene or object has symmetric or repetitive structure — the solver's own error metric can look fine while the pose is actually wrong. The Metashape Expert Manual documents this class of failure directly: symmetric and repetitive scenes are named as a root cause of alignment error, and manual markers/reference points are the documented remedy [S2]. That source does not use the specific words "mirrored" or "reflected" — this case's framing of the failure as a reflection specifically is a modeling choice, disclosed in Appendix E, made because reflection is the transformation this case's Challenges are built to test.

Appendix B — Marker Point Log

Four markers were taped to the object before scanning began. Marker 4 was logged as a matter of studio routine and is not needed for any Challenge on its own — the studio logs every marker on every job, whether or not that job turns out to need it.

MarkerExpected coordinates (client reference model, rig's local axes, cm)Actual coordinates (finished scan, same axes, cm)
Marker 1(6.10, 6.23)(9.10, 8.23)
Marker 2(-5.38, 3.30)(-2.38, 5.30)
Marker 3 (the suspect marker)(-9.47, 12.42)(9.47, 12.42)
Marker 4 (logged, not required)(-1.75, 18.73)(-1.75, -18.73)

Rig's own reported alignment error at export ("converged"): 0.40 mm RMS.

Note: marker coordinates in this appendix are a scenario construction built for this case, positioned to be consistent with a real, documented photogrammetry failure mode (see Appendix A). They are not measurements from an actual client job. Methodology: each marker's expected coordinate is a real 3-D vertex pulled directly from the Stanford Bunny's actual reconstructed mesh data (bun_zipper.ply, the same 35,947-vertex file cited in Appendix A) — specifically, the mesh's extreme vertex in +x, −y, −x, and +y respectively, with only the (x, y) components kept (z dropped) and converted from meters to centimeters, rounded to two decimals. Markers 1 and 2's actual coordinates were then built by applying one real, consistent rigid translation to their expected coordinates — a valid registration offset. Marker 3's actual coordinate was built instead by reflecting its expected coordinate across the rig's local y-axis (x → −x), with no translation. Marker 4's actual coordinate was built by reflecting its expected coordinate across the rig's local x-axis (y → −y) instead — a different mirror axis, deliberately inconsistent with Marker 3's axis. The rig's own reported 0.40 mm figure is a stated scenario value representing a plausible, misleadingly low self-reported error (see Appendix E for why it cannot be trusted at face value).

    Working Notebook

    This is a calculator, not an answer key. Type your own numbers first — then hit Check to see if your arithmetic matches. It won't tell you which option to choose; that part is still yours.

    D1 — Scan-scale note in scientific notation

    Write the Bunny's and Dragon's real vertex/triangle counts (Appendix A) in scientific notation, then find what percent of the Bunny's total raw scanned points belong to bun315.ply, the suspect pass.

    Accepted format for scientific notation: type it as 3.5947e4 or 3.5947x10^4 — either works.

    D2 — Congruence-or-similarity audit

    Use the distance formula on Appendix B's coordinates to find each marker-to-marker distance in the expected set and the actual set, then decide: congruent, similar, or neither.

    D3 — Reflection test and quadrant map

    Plot the expected markers and label each one's quadrant. Then compute where Marker 3 would land if it were reflected across the rig's y-axis instead of rotated, and compare to its actual scanned position.

    D4 — Translation check

    Using only Markers 1 and 2 (the ones D2/D3 show are not mirrored), set up and solve a system of two equations for the (Δx, Δy) translation offset. Use it to predict Marker 3's position under a pure translation, then see how far that prediction is from where Marker 3 actually landed.

    D5 — Registration-error-per-minute comparison, and a deadline check

    Using Option A's and Option B's stated registration error (Appendix B/E) and technician minutes (Appendix C), compute each option's ratio of millimeters of error to minutes spent. Then check whether Option B fits before the deadline.

    Reveal

    While everyone was building their case for Option A or Option B, the studio's QA lead ran Marker 4 — the one nobody thought they needed — through the same check anyway, just out of habit.

    It doesn't match its expected position either. But look closely at Appendix B: is Marker 4's mismatch consistent with the same mirror axis as Marker 3, or a different one? Work it out from the coordinates yourself — they've been sitting in the table the whole time.

    If the mismatch isn't confined to one predictable axis, does a three-marker manual recheck — Option B exactly as scoped in Challenge 3 — actually cover the real problem? Or does "checking the scan" now mean something bigger than three markers can tell you?
