Overview

Devon Achebe has two terminal windows open side by side, and one of them is still running.

The left window reads recursive_rollup_test... PASS, account hierarchy after account hierarchy — each pass another quiet confirmation that the function does exactly what its induction argument says it must. The right window holds a chart on Devon's second monitor, still climbing, its line pushing further into red every time the test suite reaches an account nested a little deeper.

It's the night before the release freeze for Meterworks' billing engine, and Devon decides which version of RollUpCharges ships — the function that walks every customer's nested account tree, turning raw usage events into the number that lands on somebody's invoice. Ship the wrong version, and customers could get billed the wrong amount, or the night's whole invoice run could hang.

Devon pulls the two branches up side by side. On the left: fewer lines of code, and a written proof — base case and inductive step — that the recursive version is correct for a hierarchy of any depth. On the right: no proof, just a comment reading // walked this by hand, seems fine, and a runtime graph that barely moves no matter how deep the tree goes.

One fact Devon has to take as given tonight: the left-hand version runs fine on some computer setups. But on the setup this company will actually use, it doesn't get a speed-up trick some other setups get — so it can go from fast to explosively slow as the account structure nests deeper, with no way around that on this company's setup.

Devon's phone buzzes, face-down. A message from the platform team, subject line visible: which language runtime the release will actually ship on.

Devon doesn't turn it over yet.

Background

Devon Achebe is a senior software engineer on the Billing Aggregation team at Meterworks, a usage-metering and billing platform that other software companies plug into so they can bill their own customers by consumption — API calls, compute-seconds, storage, however each customer's product is metered. Devon owns RollUpCharges, the function that turns raw usage events into a final billing total for every account in Meterworks' system, including accounts nested inside other accounts — a parent organization with sub-accounts, sub-accounts with their own sub-accounts underneath, arbitrarily deep (SEE APPENDIX A). The function is recursive by nature: computing a parent account's total requires first having the already-computed totals of every child account beneath it.

Two implementations are ready to ship, and Devon must recommend one before the release freeze.

The Provable Path is written as a direct translation of that recursive definition: a base case for an account with no children, and an inductive step that combines a parent account's own usage events with the already-computed totals of its children. Because it mirrors the mathematical recurrence exactly, Devon can prove — by induction on hierarchy depth — that it produces the correct total for every account, at every depth (SEE APPENDIX B).

The Guaranteed Floor rewrites the same logic as an explicit loop over a flattened, depth-ordered list of accounts, with a per-call cost that holds steady no matter how deep any one hierarchy goes. Its correctness rests on a walkthrough of representative test hierarchies, not a proof (SEE APPENDIX C).

The two implementations' real runtime cost does not diverge by one fixed amount — it depends on a simple fact about the computer setup Meterworks actually ships the billing engine on: some setups have a speed-up trick that makes the recursive version's repeated step almost free, and some don't (SEE APPENDIX B and APPENDIX D — that trick has a technical name, defined in Appendix G for anyone who wants to look it up). On a setup that has the trick, the two implementations run close to identically fast. On a setup that doesn't, the recursive version costs substantially more per call, and the gap widens further — explosively — as hierarchy depth grows (SEE APPENDIX D). Meterworks' billing pipeline runs against a fixed nightly compute budget and a fixed per-batch latency SLA that the next release must not miss (SEE APPENDIX A).

Billing-aggregation code carries its own history at Meterworks: the team has already shipped one production defect where a recursive rollup's own assumption — true at the top of an account tree — silently failed once an already-aggregated intermediate result was fed back into the same function one level down, producing a billing total that did not match reality. That incident is why a formal correctness argument is on the table for this release at all, not only a performance question — a documented industry precedent of exactly this failure shape exists outside Meterworks as well (SEE APPENDIX E). Full source citations for every figure in this case are in APPENDIX F.

    Step 1 — Count base-case and inductive-step invocations on a chain hierarchy

    D2/D3 warm-up. RollUpCharges's recursion trace (Appendix B's diagram is one worked example) has exactly one call per account. Pick a simple chain hierarchy — a root account, with one child, with one child, and so on — of a depth you choose (the number of accounts in the chain, root included). Only the single deepest account (no children) is a base-case call; every account above it is an inductive-step call.

    Step 2 — Percent difference between iterative and recursive, at a depth and TCO scenario you pick

    D3/D4 arithmetic. Pick one of Appendix D's three depths and one of its two recursive columns. Compute the percent difference between the recursive figure and the iterative figure at that exact cell, using the formula (recursive − iterative) ÷ recursive × 100. This is the same kind of calculation D4/D5 need — the calculator checks your arithmetic, it does not tell you which depth/scenario to use for your own D5 recommendation.

    Twist

    Ask your facilitator before revealing this — in a live discussion, the Twist is dropped at a specific moment, not read in advance.

    Reveal the Twist

    There's a real company — not Meterworks, a real one — whose recursive billing-aggregation function looked exactly like the Provable Path. It was proven correct on paper. It shipped anyway. And in production, it silently violated its own inductive assumption once an already-computed result got fed back into it one level down — two customer accounts' billing totals came out on opposite sides of zero for the same real numbers.

    That's not a story invented for this case: it's a real, publicly documented production postmortem (Appendix E, [S3]) from a real database company's founder.

    If a proof like the one you wrote for D1 can still fail in production when the implementation doesn't actually match the proof's own assumptions at every call site — does that make you trust the Provable Path more, or less, than you did five minutes ago? What exactly would you have to check, beyond writing the proof itself, to be sure this doesn't happen to Devon's version?
