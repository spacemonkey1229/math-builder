> addendum" to that canonical file; on graduation it was reframed as the authoritative, complete

## The shape of this project

Math Builder is a **local content-generation pipeline with a static artifact viewer** —
output is a folder of `.docx`/`.xlsx`/`.html` files plus one dashboard that reads a JSON
read-model off disk. It is not a hosted Operator Cockpit, not a deployed multi-user web app, and
not a physical product — there is no server, no login, no database, no deploy step. Everything
runs from the command line against the local filesystem, and the deliverables are files a guide
opens directly.

## The actual stack

- **Authoring & pipeline scripts** — Python 3, stdlib plus `python-docx` (Word generation),
  `openpyxl` (Excel generation). No package beyond those two; no virtualenv-managed dependency
  tree to maintain.
- **Read-model** — flat JSON files under `readmodel/` (`standards_spine.json`,
  `cases_index.json`, `submissions.json`, `score_overrides.json`, `domains.json`,
  `domain_coverage.json`, `reconcile_queue.json`). No database. Every write is preceded by a
  snapshot to `readmodel/_snapshots/<file>.<timestamp>` (MCS-22) — this project's substitute for
  transactional safety.
- **Dashboard / student view** — single-file HTML + vanilla JS + inline CSS
  (`app/dashboard.html`, `app/student.html`), generated by `app/build_dashboard.py` which inlines
  the JSON read-model directly into the page at build time. No framework, no bundler, no build
  step beyond running the Python generator. Opened via `file://`, not served.
- **Interactive case artifacts** — single-file HTML per case (e.g.
  `cases/cold-chain/published/Cold Chain - Interactive.html`), inline SVG only (MCS-37 — no
  external image dependencies), vanilla JS self-checking calculators, `localStorage` for a
  student's own in-session progress (checklist state, notes) — safe here specifically because
  there is no server and no cross-device requirement to break.
- **QA / gating** — pure Python scripts, no external services: `tier1_structural.py` (mechanical
  structural checks), `tier2_probes.py` (simulated-play probes, some requiring a fresh subagent),
  `tier3_verify.py` (human dry-run gate), `score_submission.py` + `guide_confirm.py` +
  `cohort_rollup.py` (submission scoring). All run from the command line against the local
  filesystem.
- **Source verification** — a web-fetch tool at authoring time only, to confirm every cited
  figure and every glossary URL (MCS-21, MCS-39) before it's written into a case. Nothing is
  fetched at runtime; the QA sandbox this project's scripts run in has no outbound network, which
  is why Tier 2 probe 6 (data decay) and Tier 1's URL checks are DELEGATED rather than
  self-executing.

## What this project deliberately does NOT have

- No hosting, no deploy step, no CI. Nothing here needs to be "live" for anyone but the person
  running the scripts locally and the guide opening the dashboard file.
- No auth. Guide/student separation is done at **generation time** (MCS-34 — `build_student()`
  produces a genuinely separate, redacted payload), not at runtime with a login gate.
- No database. `readmodel/*.json` plus snapshot-before-write is the entire durability model.

## If this ever needs to change

If a future need shows up — real hosting, multiple concurrent guides, a shared login — treat it
as a new architectural decision for this project specifically, not an inherited default from
elsewhere. Write the decision and its reasoning into `DECISIONS.md`.
